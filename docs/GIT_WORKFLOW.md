# Git workflow

## Structure

```text
main
├── setup/flutter
├── ui/sign-in
├── ui/today
├── ui/goals
├── ui/add-goal
├── ui/camera-check-in
├── ui/post-check-in
├── ui/feed
├── ui/friends
├── ui/this-week
├── ui/reminders
└── docs/workflow
```

These are retained import branches. Each starts from the integrated main at that point, then merges back into main. They are not independent app versions. The `checkpoint-4-initial-ui` tag marks the completed import.

## Commit size

Keep one coherent UI change in a commit: a labeled field, a button and its callback, a progress chart, a settings row, or one repeated row widget. Include the label, spacing, and control together. Rows generated by one loop stay in the same commit because they share one implementation. Do not split a label into word-level commits.

## Future changes

Start from current main, then create a focused branch, for example `ui/goals-edit-form` or `feature/check-in-capture`. Commit a complete, reviewable piece at a time. Open a pull request, describe the behavior and checks, then merge with a merge commit to preserve the branch's history.

```sh
git switch main
git pull --ff-only
git switch -c ui/goals-edit-form
# Make and check a focused change.
git add lib/screens/proof_screens.dart
git commit -m "Add weekly target control to goal form"
git push -u origin ui/goals-edit-form
```

Review changed screens in the emulator before merging. Keep main synced with origin after merges. Never backdate commits or attribute work to someone who did not author it.

## Repository contents

Track the Flutter source, native scaffolding, dependency lockfile. Keep generated builds, local SDK paths, credentials, coursework PDFs, LaTeX documents, and submission archives outside Git.
